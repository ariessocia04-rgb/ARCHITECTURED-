# 1PLAN — THE OFFICIAL TECA EXECUTION CONSTITUTION (ROS)

## 1. PROJECT VISION
The ARCHITECTURED Repair Operating System (ROS) is a complete enterprise-grade SaaS designed for the global repair industry (Cellphone, Laptop, Tablet). The platform is architected to be the world's most comprehensive and scalable system, supporting unlimited horizontal and vertical expansion.

## 2. ENTERPRISE PRINCIPLES
- **One SaaS / One Business Engine**: Unified platform logic.
- **One Wireflow / One Database**: Consistent interaction and data integrity.
- **Shared Architecture / Shared Components**: Zero redundancy across modules.
- **Role & Permission Based Access**: Granular security and capability control.
- **No Duplicate Architecture**: Design once, use everywhere.
- **Architecture Preservation**: TECA must maintain the approved design at all costs.

## 3. TECA EXECUTION STAGES
TECA follows an 8-stage execution pipeline for all project tasks:

1. **Repository Discovery**: Deep inspection of existing code and baseline architecture.
2. **Requirements Engineering**: Gathering, normalizing, and generating precise specifications.
3. **Planning & Roadmap**: Updating 1PLAN.md to align with organizational goals.
4. **Component Generation**: Building agents.yaml, tasks.yaml, crew.py, and implementation logic.
5. **Project Organization**: Enforcing folder structures, modularization, and naming standards.
6. **Validation Gate**: Automated and manual checks for CrewAI and architecture compliance.
7. **Long-Term Memory Integration**: Retrieving and storing organizational knowledge.
8. **Repository Publishing**: Managed commits and pull requests via the Repository Provider.

## 4. ARTIFACT FLOW & ORGANIZATION
All artifacts generated by TECA must follow the **Technician Gold Standard**:
- **Applications/**: Isolated role-based workspaces (Technician, Owner, Front Desk, Customer).
- **Repair Operating System (ROS)/**: The Core Platform and Shared Business Modules.
- **.teca/memory/**: Persistent organizational intelligence.
- **logs/**: Execution history and audit trails.

## 5. OWNER SUPER ROLE PRINCIPLE
The Owner is a **SUPER ROLE**. It is not a separate application but a role with full visibility that inherits capabilities from the shared platform.
- The Owner uses existing Technician and Front Desk modules.
- Access isgoverned by the Permission Engine; architecture remains shared.

## 6. VALIDATION GATE REQUIREMENTS
Publishing is blocked unless:
- 100% adherence to the approved ARCHITECTURED design.
- Zero duplicate modules or business logic.
- YAML and task wiring integrity verified.
- Consistency with the Volume 3 Shared UI System.

## 7. LONG-TERM MEMORY LIFECYCLE
TECA's organizational intelligence is stored in `.teca/memory/`:
- **Retrieval**: Knowledge is loaded at the start of every execution to prevent repeating mistakes.
- **Learning**: Successes, failures, and lessons learned are recorded post-execution.
- **Improvement**: Memory is used to enrich future component generation and validation.

## 8. GOVERNANCE RULES
- **Single Source of Truth**: GitHub is the final authority.
- **No Redesign**: Architecture is protected; redesigning the approved system is forbidden.
- **Modular Isolation**: Every module must reside in its own folder with zero logic leakage.
- **Constitutional Authority**: This document is the supreme Constitution. If conflicts arise, 1PLAN.md prevails.
